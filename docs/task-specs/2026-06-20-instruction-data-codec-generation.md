# Instruction Data Codec Generation

## Why

AQAMI-generated instruction modules already exposed typed execution-preparation and dispatch helpers.

That was a strong boundary, but the generated surface still stopped short of the first byte-level contract a Solana program actually needs:

- a deterministic discriminant for each instruction
- an explicit mapping between bytes and typed AQAMI args
- a safe way to bind decoded instruction data to any required typed account-data context
- a byte-driven path into the existing dispatch-preparation boundary

The next coherent step was to generate that instruction-data codec explicitly in `instructions/mod.rs`.
That lets AQAMI own a reviewable generated byte contract without pretending the framework already has a stable public serialization standard or hidden generic account decoding.

## Scope

In scope:

- generate a program-level instruction-data enum with explicit discriminants
- generate per-program encode helpers for instruction args
- generate per-program decode helpers with structured error reporting
- generate typed instruction/account-data binding helpers
- generate a byte-driven dispatch-preparation helper on top of the existing typed dispatch contract
- update generated-program tests and fixture expectations
- update project docs so current-state descriptions match the implemented surface

Out of scope:

- a framework-wide stable external wire-format guarantee
- generic account-state deserialization from raw bytes
- on-chain entrypoint generation
- client SDK generation
- MCP server work

## Constraints

- keep the byte contract explicit and per-program
- do not hide serialization behavior behind runtime magic
- preserve deterministic generation
- prefer typed errors over opaque decode failures
- do not let docs imply AQAMI has standardized more than it actually has

## Options Considered

### 1. Keep byte handling out of generated code entirely for now

Pros:

- avoids defining any byte-level contract yet

Cons:

- leaves generated dispatch incomplete for real Solana instruction flow
- makes tests and future entrypoints invent their own temporary byte conventions
- creates pressure for ad hoc handwritten glue instead of an explicit generated surface

### 2. Generate an explicit per-program codec now

Pros:

- makes instruction bytes part of the reviewable generated contract
- keeps decoding logic deterministic and inspectable
- composes cleanly with the existing typed dispatch-preparation boundary
- strengthens future entrypoint, client, and MCP work without forcing hidden runtime decoding

Cons:

- expands the generated API surface
- requires careful docs wording so the repository does not overclaim wire-format stability

## Chosen Approach

Option 2.

AQAMI should generate an explicit per-program instruction-data codec now.
That is the smallest honest step from typed dispatch toward real instruction flow, and it preserves the repository's preference for explicit machine-readable behavior over hidden conventions.
